# 开发记录：Excel 内嵌预览

## 需求概述

在笔记中用 `![[表格.xlsx]]` 内嵌显示只读表格预览，**只读不编辑**；点击文件名用系统默认程序打开 Excel。

需求提出时有两个未定问题，需先想清楚再动手：

1. Excel 有多个 sheet 怎么办？
2. Excel 内容过多怎么办？

### 功能清单

| 功能 | 说明 |
|------|------|
| 内嵌预览 | `![[表格.xlsx]]` 在阅读模式与实时预览下均显示表格 |
| 多 sheet 切换 | 预览顶部标签栏点击切换，默认显示第一个可见 sheet |
| `#sheet` 定位 | `![[表格.xlsx#销售明细]]` 直接定位到指定 sheet |
| 大表限流 | 默认只渲染前 N 行 × M 列，底部写明总行列数与当前显示行列数，可「显示全部行列」 |
| 缩放 | 底栏「适应宽度」按钮在「缩到整表可见」与「原始大小」之间切换，宽表不用横向滚动 |
| 双击/点击打开 | **不自己实现**，沿用 Obsidian 原生行为（见下） |
| 设置开关 | 第 6 个设置 Tab「Excel 预览」，4 个设置项 |

### 设计决策：两个未定问题的答案

**多 sheet → 顶部标签栏 + `#Sheet名` 子路径定位**

标签栏切换不回写笔记内容；`#Sheet名` 复用 Obsidian 用户已经熟悉的子路径习惯，不用发明新语法；默认跳过隐藏 sheet（但仍列在标签栏里并弱化显示，方便核对）。只有一个 sheet 时不渲染标签栏。

**内容过多 → 完整解析 + 限量渲染 + 容器内滚动 + 可展开**

关键是分清瓶颈：解析 5000 行 × 35 列只要 100ms 量级，**杀性能的是 DOM 节点**。所以完整解析（才能报出准确的「共 N 行 × M 列」），但只渲染窗口内的数据，表格放在固定高度容器里滚动。再叠加三层保护：

| 情况 | 处理 |
|------|------|
| 文件 > 20MB | 不解析，只保留 Obsidian 原生占位 |
| 单元格文本过长 | CSS 截断，完整内容放 `title` |
| 反复打开同一文件 | 按 `路径 + mtime + 体积` 缓存，LRU 上限 5 |

### 明确不做的事：用系统默认程序打开文件

Obsidian 原生已支持点击非 Markdown 文件用系统默认程序打开，自己再实现一遍（`shell.openPath` + 路径转换 + 平台差异）只是多一处需要维护的 Electron 调用。

由此推出一条贯穿全局的硬性约束：**保留 Obsidian 原生渲染出的 `.internal-embed` 元素本身，只往它内部追加预览容器，不整体替换它**。一旦替换掉宿主元素，原生点击打开的行为就一起没了。

## 最终方案

### 文件结构

```
src/preview/
  xlsx-mini.d.ts         ← 给 xlsx/dist/xlsx.mini.min.js 补类型声明（复用 xlsx 官方类型）
  excel-config.ts        ← 模块级配置对象 + 可预览扩展名判定
  excel-parser.ts        ← 解析、LRU 缓存、窗口化取值
  excel-table.ts         ← 表格 / 标签栏 / 状态栏 DOM 渲染（两条路径共用）
  excel-embed.ts         ← 阅读模式后处理器 + 挂载/卸载/重绘注册表
  excel-live-preview.ts  ← 实时预览的 CM6 ViewPlugin
main.ts        ← 注册编辑器扩展与后处理器、缓存失效、syncConfig 写入 excelConfig
settings.ts    ← excelPreviewEnabled / MaxRows / MaxCols / Height
setting-tab.ts ← 第 6 个 Tab「Excel 预览」
styles.css     ← .sh-excel-* 样式段
package.json   ← 新增运行时依赖 xlsx（官方 CDN tarball）
```

### 两条渲染路径（本功能最大的技术点）

官方文档 `Plugins/Editor/Editor extensions.md` 写得很明确：

> If you want to change how the document looks and feels in Live Preview, you need to build an editor extension.

也就是说阅读模式和实时预览**必须用两套机制**，Markdown 后处理器只覆盖阅读视图：

| 模式 | 机制 |
|------|------|
| 阅读模式 / 悬浮预览 | `registerMarkdownPostProcessor` |
| 实时预览（编辑模式） | CM6 `ViewPlugin`（`registerEditorExtension`） |

### 核心逻辑

```
![[表格.xlsx#销售明细]]
  → 找到 Obsidian 渲染出的 .internal-embed 宿主
  → 读 src 属性（取不到子路径时回退解析该段原文）
  → splitSubpath 拆出 路径 / 子路径
  → metadataCache.getFirstLinkpathDest 解析成 TFile
  → 扩展名在支持列表内 → 追加 .sh-excel-host 容器
  → openWorkbook（命中缓存则零 IO）
  → paintSpreadsheet：标签栏 + 表格 + 底部统计
```

实时预览侧的 ViewPlugin 监听编辑器 DOM 变动（150ms 节流），扫描 `.internal-embed` 后走同一个 `mountEmbedPreview`。刻意**不自己下 replace decoration 去抢渲染范围**，理由见「关键技术点」。

## 踩坑记录

### 错误 1：SheetJS mini 构建静默不支持 .xls / .xlsb

**做法**：按计划选用 SheetJS，并假设它能读 `.xlsx / .xls / .xlsb / .ods / .csv` 全格式。

**问题**：实测发现 mini 构建读 `.xls` 抛 `parse_xlscfb is not defined`，读 `.xlsb` 抛 `parse_sty_bin is not defined`。

**解决**：用实测而非文档决定构建选择。全量构建（+1.16MB）支持全部格式，mini 构建（+270KB 压缩后）支持 `.xlsx / .xlsm / .ods / .csv`。最终选 mini，并把 `.xls / .xlsb` **从支持扩展名列表里移除**，而不是让它们走到解析再报错——这样这两类文件保持 Obsidian 原生占位，点击仍可用 Excel 打开，不会出现「有预览框但里面是报错」。

**教训**：库的「构建变体」之间的能力差异要实测确认，不能按主包文档推断。

### 错误 2：`sheet_to_json` 的 `blankrows: false` 会让行号错位

**做法**：为让输出紧凑，取值时用 `blankrows: false` 丢掉空行。

**问题**：实测 `[标题], [], [名称,值], ...` 得到 5 行而非 6 行——空行被删掉，**后续所有行号整体前移**，而 `!merges` 里的合并区域坐标是绝对行号，于是合并单元格全部错位到别的行上。

**解决**：改用 `blankrows: true`（配合 `defval: ''` 得到空字符串单元格），保证行号与工作表真实坐标一一对应。

**教训**：凡是「坐标引用」与「行数组」并存的场景，不得在取值阶段做任何行删除。

### 错误 3：体积估算偏差 —— 项目构建不压缩

**做法**：按 `esbuild --minify` 实测的 272KB 向用户估算「mini 构建约 +270KB」。

**问题**：集成后 `main.js` 从 127KB 变成 664KB，实际 **+537KB**，约为估算的两倍。

**原因**：`esbuild.config.mjs` 没有开 `minify`，生产产物是不压缩的；我的估算基于压缩后的数字。

**教训**：估算打包体积必须用**与项目构建配置完全一致**的参数，而不是自己另配一套。

**决策**：保持不压缩。`main.js` 维持 664KB（+537KB），与插件既有的构建风格一致，产物可读、便于排查。实测开启压缩后可降至 353KB（+226KB），但会让整个产物不可读，收益不值当 —— 如需压缩，只需在 `esbuild.config.mjs` 加一行 `minify: prod`。

### 错误 4：mini 构建的 `book_new()` 不建 Workbook 元数据（测试侧）

**做法**：验证脚本里用 `wb.Workbook.Sheets[3].Hidden = 1` 造一个隐藏 sheet。

**问题**：报 `Cannot read properties of undefined (reading 'Sheets')` —— mini 构建的 `book_new()` 返回的 `wb.Workbook` 是 `undefined`，`book_append_sheet` 也不建它。

**解决**：测试里手工补 `wb.Workbook = { Sheets: [{}, {}, {}, { Hidden: 1 }] }` 再写盘。

**附带确认**：写入后再读回，`wb.Workbook.Sheets[i].Hidden` 正确为 `[0,1]`，说明解析侧读取隐藏标记的写法是对的。

### 错误 5：点标签页被 Obsidian 当成「点击嵌入」而跳转（实机反馈）

**现象**：实机使用时表格渲染正常，但点 sheet 标签页想切换时，Obsidian 反而跳转/打开了该 Excel 文件。

**原因**：预览容器是嵌在 Obsidian 渲染出的 `.internal-embed` 元素**内部**的，而这个元素自带「点击打开文件」的行为。标签页按钮的 click 冒泡到 `.internal-embed`（及其外层容器），被 Obsidian 的委托处理当成「用户点了整块嵌入」而触发打开。

**解决**：在预览容器上截断冒泡 —— `click` / `dblclick` / `mousedown` / `auxclick` 四个事件都 `stopPropagation()`，其中 `click` / `dblclick` 额外 `preventDefault()`，以防默认行为落在祖先链接上。

**为什么不改成把容器挂到宿主元素之后（做兄弟节点）**：那样确实能天然避开冒泡，但实时预览下 `.internal-embed` 可能位于 CM6 直接管理的 `cm-content` 内，往 CM6 的内容 DOM 里插节点会被后续 diff 清掉。嵌在宿主内部、只拦事件，是两种模式都安全的做法。

**为什么不会破坏「点击文件名用 Excel 打开」**：文件名标题栏是 Obsidian 自己渲染的元素，位于我们的容器**之外**，事件不经过我们的拦截层。验证脚本专门为此加了一条断言：点标题栏时事件仍能正常传播到 `.internal-embed`。

**教训**：把可交互 UI 嵌进宿主自带的「整块可点击」元素里时，必须在自己的容器边界上截断冒泡，并且要专门回归验证「宿主原有的点击行为没有被误伤」。

### 错误 6：阅读模式下预览容器被 Obsidian 覆盖，只剩文件名标题栏（实机反馈）

**现象**：实时预览正常，**阅读模式只显示 Obsidian 原生的文件名标题栏**，表格完全不出现，重新打开笔记也不恢复。

**排查**：让用户在阅读模式的控制台跑一段诊断脚本，得到关键一行 —— **「已挂载标记 = 2，预览容器 = 1」**。

这一组数字直接排除了两个最像的猜测：
- 不是「选择器没匹配上」：标记打上了，说明元素匹配、`src` 解析、文件解析、容器创建**全部成功过**；
- 不是「`src` 读不到」：同上。

容器数少于标记数，只可能是**有容器在创建之后被移除了**。

**原因**：阅读模式下 Obsidian 对嵌入元素是**两阶段渲染** —— 先产出占位，随后重写这个元素的内部内容。容器原先嵌在 `.internal-embed` 内部，于是被这次重写一并清掉。而当时的去重依据是宿主元素上的 `sh-excel-mounted` 标记类：标记还在、容器已没，导致之后所有重试都被判定为「已挂载」而直接跳过 —— 表现为**永久空白，且刷新无效**。

**解决**：三处一起改，缺一不可。

| 改动 | 作用 |
|------|------|
| 阅读模式下容器改挂在宿主元素**之后**（兄弟节点） | 宿主内部被重写波及不到容器 |
| 去重依据由「标记类」改为「容器是否真的还在」 | 容器被清掉后能够重新挂载，不再永久空白 |
| 后处理器 `sortOrder = 100` + 延时 400ms 复查一次 | 排在 Obsidian 自身渲染之后；万一元素稍后才生成也能补挂 |

**必须注意**：实时预览的容器**仍然要嵌在宿主内部**。那里是 CM6 自己管理的 widget 容器，往外挪会被 CM6 的内容 diff 清掉。所以两条路径的插入位置**本来就该不同**，由 `mountEmbedPreview` 的 `nested` 选项区分 —— 不要为了「统一」把它们改成一个位置。

**教训**：判断「某功能是否已初始化」时不要只信一个标记位，要校验**实际成果是否还在**。在别人会重写 DOM 的环境里，标记位和真实状态会脱节；一旦脱节，症状就是永久空白而不是自动重试。诊断时，「标记数 vs 实际容器数」这类**两个计数的差**比单看一个计数有用得多。

### 错误 7：点了「适应宽度」仍残留一根横向滚动条（实机反馈）

**现象**：点开「适应宽度」后表格已明显缩小，但底部仍有一根很短的横向滚动条，只多出一点点。

**两个原因叠加**：

1. **取整误差** —— `offsetWidth` / `clientWidth` 返回的是**取整后的整数**。表格真实宽度若是 1234.6px，读到的是 1234，据此算出的比例偏大，渲染后溢出零点几像素；而浏览器只要检测到溢出就会画出滚动条。
2. **主题样式泄漏** —— 阅读模式下我们的表格位于 `.markdown-rendered` 之内，主题里 `.markdown-rendered table` 这类规则权重是 (0,1,1)，**高于**原来的单类名 `.sh-excel-table` (0,1,0)，于是 `margin` / `border-spacing` / `padding` 被主题盖回来，凭空多出横向宽度。用户当时就猜「可能是 margin 的问题」，方向是对的。

**解决**：三处一起改。

| 改动 | 作用 |
|------|------|
| 比例计算留 1px 余量：`(可用宽 - 1) / 自然宽` | 抵消取整误差 |
| 应用后再按实测 `scrollWidth - clientWidth` 收最多 3 轮，每轮瞄准「可用宽 - 1px」 | 兜住边框、外边距等一切估算里没有的量 |
| 表格样式统一加 `.sh-excel-preview` 前缀，并显式 `margin: 0; border-spacing: 0` | 权重升到 (0,2,0)，压过主题规则 |

**为什么每轮瞄准「可用宽 - 1px」而不是「可用宽」**：对**恒定**偏移（边框、外边距），纯按比例修正只能无限逼近边界、收敛很慢（实测第一轮后还差 0.004px，虽小但断言上仍算溢出）。把目标设在边界内侧 1px，两轮内就落进区间。

**取舍**：缩放下限 0.4 **优先于**「一定不溢出」。可用宽度窄到需要缩到 0.4 以下时，宁可保留横向滚动，也不把字缩到看不清 —— 这是刻意行为，不是缺陷。

**教训**：用「量一次、算个比例」做自适应布局时，**测量值本身就有误差**（取整、边框、外边距、主题样式泄漏），必须留余量或按实测结果迭代修正。否则边界情况下会留下肉眼可见但极难解释的残留 —— 比如一根只剩几像素的滚动条。

## 关键技术点

### 为什么实时预览不自己下 replace decoration

Obsidian 自己已经在实时预览里把 `![[a.xlsx]]` 渲染成了 widget。再对同一范围下 `Decoration.replace` 有冲突风险，而且要自己处理光标位置判断。改为**等 Obsidian 渲染完成后往容器里追加**，好处：

- 不与原生渲染抢范围；
- 顺带满足「不替换宿主元素」的约束，原生点击行为原封不动；
- 自动继承 Obsidian「光标落在这一行时显示原文、移开时显示渲染结果」的行为，不用自己判断光标。

代价是依赖 `.cm-embed-block` / `.internal-embed` 这类内部类名，因此选择器集中定义、失败时降级为只显示原文（原生点击不受影响）。

### 为什么取值用 `raw: false`

`sheet_to_json` 的 `raw: false` 让 SheetJS 返回**按单元格格式格式化后的文本**，一举解决日期显示成 `45000` 这类序列号、以及千分位/小数位等数字格式问题——这正是自己做解析器最容易翻车的地方。实测日期列输出 `1/1/26` 形式而非序列号。

### 为什么缓存 WorkBook 而不是转换后的行数组

SheetJS 在 `read` 阶段就已经把工作表解析成单元格对象，这部分内存无论如何都要占。缓存行数组只会在其上再叠一份；而保留 WorkBook 可以**按需只转换要显示的那个窗口**（`sheet_to_json` 的 `range` 参数），「显示全部行列」时也能从同一份缓存重新取值，不必二次读盘。

### `splitSubpath` 的处理顺序

先按 `|` 去别名 → 再按 `#` 切分 → **最后才解码**。

顺序反了会把文件名里的 `%23` 解码成 `#`，进而被误判成子路径分隔符。实测 `a%23b.xlsx` 正确解析为路径 `a#b.xlsx`、无子路径。

### 首行表头的启发式判断

首行单元格全部非空、且不含纯数字时才当作表头放进 `<thead>`，否则整表平铺。避免把「首行就是数据」的表格错误加粗成表头。

### 隐藏 sheet 的读取

`wb.Workbook.Sheets[i].Hidden` 与 `SheetNames[i]` 同序对应。默认展示取第一个 `Hidden` 为假的工作表；全部隐藏时回退到第一个。

### 为什么缩改用 CSS `zoom` 而不是 `transform: scale()`

`transform: scale()` 只是**视觉**缩放，元素的布局尺寸不变 —— 缩完之后表格仍按原始宽度占据布局空间，结果是滚动条长度对不上、右侧空出一大片。`zoom` 会真正参与布局重排，滚动区域和容器高度自动跟着变，才是「表格缩放」该有的手感。Obsidian 桌面端是 Chromium，`zoom` 原生支持（`isDesktopOnly: true` 已满足前提）。

配套的几个细节：

- **必须在未缩放状态下量取自然宽度**：先清掉 zoom 再读 `offsetWidth`，否则量到的是上一轮的缩放值。
- **只缩不放**：本来就装得下就保持原始大小，不放大 —— 避免「适应宽度」把小表撑成大字号。
- **设下限 0.4**：列特别多时缩到 0.4 就不再往下缩了，宁可保留横向滚动，也不把字缩到看不清。
- **留 1px 余量并按实测迭代**：测量值有取整误差，估算里也没有边框和外边距，所以先按 `(可用宽 - 1) / 自然宽` 起步，再按实测 `scrollWidth` 收最多 3 轮。目标是**横向不出现滚动条**（详见错误 7）。
- **表格样式要压过主题**：选择器统一写成 `.sh-excel-preview .sh-excel-table`，并显式 `margin: 0; border-spacing: 0`，否则 `.markdown-rendered table` 一类主题规则会盖回来、凭空多出横向宽度。

最终行为：**横向不出现滚动条**（缩放下限 0.4 触底时除外），**纵向高度超过预览框高度时照常出现滚动条** —— `max-height` + `overflow: auto` 不受缩放影响。

菜单位置上，「适应宽度」与「显示全部行列」是两个**互不相关**的开关：前者管缩放（怎么看），后者管渲染多少行列（看多少）。刻意不做成一个按钮，因为「缩到可见」和「渲染全部」是两件事，合并后无法只做其中一件。

## 已知限制

| 限制 | 说明 |
|------|------|
| 不支持 `.xls` / `.xlsb` | SheetJS mini 构建不含对应解析器，这两类文件保持 Obsidian 原生占位，点击仍可用 Excel 打开 |
| 体积 | 引入 SheetJS 后 `main.js` 由 127KB 增至 664KB（未压缩），约为原来的 5 倍 |
| 不做列宽还原 | 表格按内容自适应，不等同 Excel 的列宽；单元格文本过长会截断显示，完整内容在 `title` 里 |
| 不做公式计算 | 显示的是工作簿中缓存的公式结果值，即 Excel 最后一次保存时算出的值 |
| 依赖内部类名 | `.internal-embed` / `.cm-embed-block` 非公开 API，Obsidian 大版本变更时可能失效 |
