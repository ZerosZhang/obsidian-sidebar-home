## 标签页复用与强制新标签页

> 日期：2026-07-21 | 版本：v2.2.0

### 概述

基于 `external/obsidian-open-in-new-tab-master` 参考插件，将 Open In New Tab（强制新标签页打开）与 sidebar-home 已有的 `reuseExistingTab`（复用已有标签页）合并为一个统一功能。同时修复 wiki 链接 `[[file]]` 不触发复用逻辑的 Bug。

**功能入口：** 设置页 → 标签页设置 → 「复用已有标签页」开关。

| 场景 | 文件是否已打开 | 行为 |
|------|--------------|------|

| wiki 链接（跨文件 `[[note]]`） | 已打开 | `setActiveLeaf` 跳转，原方法 `newLeaf=false`（保留标题跳转） |
| wiki 链接（跨文件 `[[note]]`） | 未打开 | 原方法 `newLeaf=true`（新建标签页） |
| 文件浏览器点击 | 已打开 | `stopPropagation` + `preventDefault` + `setActiveLeaf` |
| 文件浏览器点击 | 存在空白标签页 | `setActiveLeaf` 到空白页，不阻止默认行为 |
| 文件浏览器点击 | 未打开，无空标签页 | `stopPropagation` + `preventDefault` + `openLinkText(path,path,true)` |
| 侧边栏快链 | 已打开（rootSplit 内） | `revealLeaf` + `setActiveLeaf({focus:true})` |
| 侧边栏快链 | 未打开 | `getLeaf('tab')` + `openFile()` + 切换阅读模式 |

当 `reuseExistingTab = false`：全部透传 Obsidian 默认行为。

### 2. 踩坑记录

#### 错误 1：monkey-around 导致 openLinkText 不触发

**现象：** 使用 `import { around } from 'monkey-around'` 的 `around(Workspace.prototype, { openLinkText(old) { ... } })` 方式 monkey-patch 后，点击 wiki 链接没有打开新标签页。

**分析：** `monkey-around` 的 `around1` 内部对原型方法做了多层 `setPrototypeOf` 包装。当 Obsidian 的 `Workspace` 类继承链较深（`Workspace extends Events`），`Object.getPrototypeOf(obj)[method]` 解析可能绕过被 patch 的方法；同时 `hadOwn` 判断在 Obsidian 的类结构中不稳定。

**解决：** 放弃 `monkey-around`，改用直接原型赋值 + 闭包保存原始引用：

```typescript
export function patchOpenLinkText(plugin: SidebarHomePlugin): () => void {
    const original = Workspace.prototype.openLinkText;
    Workspace.prototype.openLinkText = async function(...) {
        // ... 自定义逻辑
        return await original.apply(this, [...]);
    };
    return () => { Workspace.prototype.openLinkText = original; };
}
```

`onunload` 中调用返回的卸载函数恢复原始方法。

---

#### 错误 2：路径严格比较导致跨文件夹匹配失败

**现象：** wiki 链接 `[[note]]` 指向 `folder/note.md`，`reuseExistingTab` 开启但已经打开的 `folder/note.md` 未被识别，每次点击都创建新标签页。

**原因：** 第一版使用 `viewState.state?.file === \`${fileName}.md\`` 做严格相等比较。在 Obsidian 中，`viewState.state.file` 存储完整相对路径（如 `folder/note.md`），而 wiki 链接解析出的 `fileName` 不含文件夹前缀（如 `note`），`===` 永远不匹配。

**解决：** 改用 `endsWith`：

```typescript
const file = (vs.state as { file?: string })?.file;
if (vs.type === 'markdown' && file?.endsWith(`${fileName}.md`)) {
    // 匹配成功
}
```

文件浏览器处理器使用 `===` 即可（因为 `data-path` 属性本身就是完整相对路径）。

---

#### 错误 3：TypeScript `unknown` 类型阻塞编译

**现象：** `tsc -noEmit` 报错 `Object is of type 'unknown'`，指向 `vs.state?.file?.endsWith(...)`。

**原因：** `WorkspaceLeaf.getViewState()` 返回的 `ViewState` 接口中 `state` 字段类型为 `unknown`（Obsidian 类型声明为 `any` → `tsconfig` 中 `noImplicitAny: true` 迫使类型推断为 `unknown`），不能直接访问 `.file`。

**解决：** 使用类型断言：

```typescript
const file = (vs.state as { file?: string })?.file;
```

---

#### 错误 4：`newLeaf='tab'` 字符串与 `newLeaf=true` 布尔值行为差异

**现象：** 参考插件使用 `openLinkText(path, path, true)`（布尔），第一版用 `'tab'`（字符串）。`'tab'` 在 `PaneType` 类型定义中合法，但实际行为可能因 Obsidian 版本而异。

**解决：** 统一使用 `true`（布尔），与参考插件 `openInNewTab` 及 `obsidian-no-dupe-leaves` 一致。Obsidian 的 `getLeaf(true)` 和 `getLeaf('tab')` 行为等价，但 `true` 历史更久、兼容性更好。

---

#### 错误 5：文件浏览器已打开文件时仍调用 openLinkText

**现象：** 第一版在文件浏览器处理器的"找到已打开文件"分支中，调用 `workspace.openLinkText(path, path, false)`，导致我们的 `patchOpenLinkText` 再次被触发并执行重复的 `iterateAllLeaves`。

**解决：** 已找到文件时直接 `stopPropagation` + `preventDefault` + `setActiveLeaf`，不额外调用 `openLinkText`。

## 关闭标签页后跳转到前一个标签页

### 需求概述

Obsidian 原生行为：关闭标签页后，激活后一个（右侧）标签页。本功能改为：关闭标签页后，激活前一个（左侧）标签页；关闭第一个标签页时保持默认行为不变。

#### 功能清单

| 功能 | 说明 |
|------|------|
| 跳转前一个 | 关闭活跃标签页后激活左侧相邻标签页 |
| 覆盖所有关闭途径 | X 按钮 / Ctrl+W / 右键菜单"关闭" / 双击关闭均生效（最终都走 `leaf.detach()`） |
| 第一个标签页不干预 | 关闭最左侧标签页时保持 Obsidian 默认行为 |
| 非活跃标签页不干预 | 关闭后台标签页时不做任何切换 |
| 设置开关 | 设置页"标签页"Tab 新增「关闭标签页后跳转到前一个」（`closeTabGoToPrev`，默认开启） |

#### 行为矩阵（`closeTabGoToPrev = true` 时）

| 场景 | 行为 |
|------|------|
| 关闭活跃标签页（非第一个） | Obsidian 默认激活后一个 → 改为激活前一个 |
| 关闭活跃标签页（第一个） | 不干预，保持默认（激活后一个） |
| 关闭非活跃标签页 | 不干预，活跃标签页不变 |
| 关闭最后一个标签页 | 不干预（Obsidian 本就激活前一个） |

---

### 最终方案

#### 文件结构

```
settings.ts    ← 新增 closeTabGoToPrev 设置项（默认 true）
setting-tab.ts ← "标签页" Tab 新增开关
tab-utils.ts   ← 新增 patchCloseTabGoToPrev()（detach patch + layout-change 消费）
main.ts        ← onLayoutReady 注册、onunload 还原（与 patchOpenLinkText 同模式）
```

#### 核心逻辑

```
用户关闭标签页
  → WorkspaceLeaf.prototype.detach（被 patch 拦截）
      → detach 前同步记录：叶子顺序、被关闭叶子 index、是否活跃、前后邻居
      → 调用原始 detach
  → Obsidian 完成激活（默认激活后一个），触发 layout-change
      → 消费记录：若 被关闭的是活跃叶子 && 非第一个 && Obsidian 激活了后一个
          → setActiveLeaf(前一个, { focus: true })
```

#### 叶子顺序获取（DOM 方案）

```typescript
const getRootLeavesInOrder = (): WorkspaceLeaf[] => {
    // .workspace-tab-header 按视觉从左到右排列，排除左右侧边栏
    const headers = Array.from(document.querySelectorAll<HTMLElement>('.workspace-tab-header'))
        .filter((h) => !h.closest('.mod-left-split, .mod-right-split'));
    if (headers.length === 0) return [];
    // leaf.tabHeaderEl 反查匹配（与 main.ts 双击关闭同款先例）
    const byHeader = new Map<HTMLElement, WorkspaceLeaf>();
    workspace.iterateAllLeaves((leaf) => {
        const tabHeaderEl = (leaf as any).tabHeaderEl as HTMLElement | undefined;
        if (tabHeaderEl) byHeader.set(tabHeaderEl, leaf);
    });
    return headers.map((h) => byHeader.get(h)).filter((l): l is WorkspaceLeaf => !!l);
};
```

### 踩坑记录

#### 错误 1：detach 返回后同步判断 activeLeaf 失效

**做法**：patch `WorkspaceLeaf.prototype.detach`，`original.call(this)` 返回后立即检查 `workspace.activeLeaf === nextLeaf`，是则 `setActiveLeaf(prevLeaf)`。

**问题**：功能完全不生效。Obsidian 在 detach 流程中会同步触发 `active-leaf-change` / `layout-change`，detach 返回时 `activeLeaf` 可能仍是旧值或临时值，同步判断拿不到"Obsidian 最终激活了谁"。

**调试证据**：控制台日志显示 `original detach done, activeLeaf after = 新标签页`——detach 刚返回时 Obsidian 激活的是一个空的"新标签页"占位，真正激活后一个标签页发生在后续流程。

**解决**：改为两段式——detach 时**同步记录上下文**（此时 `activeLeaf` 还是关闭前的值，信息准确），在 **`layout-change` 回调中消费**（此时 Obsidian 已完成激活）。`closeInfo` 在 detach 前写入、layout-change 时读取并置空。

**教训**：Obsidian 的标签页激活流程跨越多个内部阶段，不能在 detach 返回后同步假设激活已完成。用"发起时记录、布局事件后消费"的模式避免时序问题。

---

#### 错误 2：iterateRootLeaves 在标签页组/浮动标签页布局下返回不全

**做法**：用 `workspace.iterateRootLeaves()` 收集主区域叶子作为顺序依据。

**问题**：`index` 恒为 `-1`，前后邻居均为 null，功能不生效。调试日志显示实际打开了 3 个标签页，`iterateRootLeaves` 只返回 1 个叶子——活跃叶子根本不在遍历结果中。

**原因**：Obsidian 1.7+ 引入标签页组（Tab Groups）、浮动标签页等新布局后，`rootSplit` 的树结构与早期版本不同，`iterateRootLeaves` 遍历不全，不再可靠地反映主区域全部标签页。

**解决**：放弃 `iterateRootLeaves`，改用 DOM 顺序——查询所有 `.workspace-tab-header`（视觉从左到右），用 `closest('.mod-left-split, .mod-right-split')` 排除左右侧边栏，再通过 `leaf.tabHeaderEl` 反查匹配 leaf。浮动标签页也在 `.mod-root` 内，天然被覆盖。

**教训**：不要假设遍历 API 返回完整的视觉顺序。Obsidian 布局机制随版本演进，DOM 顺序是最终的视觉事实，`tabHeaderEl` 反查 leaf 是可靠的桥接方式（项目双击关闭功能已有同款用法）。

---

#### 错误 3：调试日志定位问题

**做法**：在 patch 安装、detach 调用、layout-change 消费三个关键点输出 `[TabClose]` 日志（叶子列表、index、activeLeaf、邻居）。

**价值**：
1. 确认用户运行的是新代码（`patch installed` 日志）
2. 一次定位根因（`leaves = (1)`, `index = -1` 暴露 iterateRootLeaves 问题）
3. 验证修复后行为正确（`switching to previous leaf` 日志出现）
4. 确认边界行为（`closedActive = false` 时不干预）

**收尾**：功能验证通过后移除全部调试日志再发布正式版。

**教训**：功能不生效且无报错时，先加关键路径日志确认"代码在跑、数据是什么"，再谈修复。

### 关键技术点

#### 为什么不用 layout-change 快照对比方案

最初考虑过纯事件方案：维护上一次的叶子列表快照，`layout-change` 时对比找出被关闭的叶子。但"关闭前谁是活跃叶子"这个信息无法可靠获取——关闭引起的 `active-leaf-change` 先于 `layout-change` 触发，快照中的活跃叶子已被污染。detach patch 在关闭发起时同步记录，信息最准确。

#### 为什么不在 detach 内直接 setActiveLeaf

detach 返回后 Obsidian 的激活流程尚未结束（会先激活占位"新标签页"再激活后一个），立即干预会被后续流程覆盖。`layout-change` 回调是 Obsidian 完成布局更新后的稳定时机。

#### 判断条件的三重保险

```
closedActive  ← 只处理关闭活跃标签页
prevLeaf      ← 非第一个标签页（index > 0）
activeLeaf === nextLeaf ← 仅当 Obsidian 默认激活了后一个才干预
```

第三重条件保证了关闭最后一个标签页（Obsidian 本就激活前一个）和跨标签页组等复杂场景下不做错误干预。

## 右键菜单自定义

### 需求概述

2. 新增右键菜单自定义功能，支持三个区域（文件资源管理器、编辑器、标签页标题）的菜单子项显示/隐藏

### 右键菜单拦截

- 使用 `MutationObserver` 监听 `document.body`，等待 `.menu` 元素出现
- 直接查询文档中的 `.menu-item` 元素进行发现和隐藏
- 隐藏后在同一回调中清理多余的分隔线

### 踩坑记录

#### 错误 1：用 `requestAnimationFrame` + `menu.items` 操作 DOM

**做法**：在 `file-menu` 事件回调中用 `requestAnimationFrame` 延迟，然后遍历 `menu.items` 数组，通过 `item.dom` 设置 `style.display = 'none'`。

**问题**：`item.dom` 是**孤立的 DOM 节点**，尚未挂载到文档中。设置其 `style` 对文档中实际渲染的菜单无效。

**验证方式**：检查 `item.dom.parentElement` 返回 `undefined`，证明节点未挂载。

**解决**：放弃 `menu.items`，改用 `MutationObserver` 等菜单出现在文档后，直接查询文档中的 `.menu-item` 元素操作。

**教训**：`menu.items` 中的 `dom` 属性指向的是菜单内部创建的元素引用，但在 `showAtMouseEvent` 调用前，这些元素并未 append 到文档树中。不能假设 `requestAnimationFrame` 时菜单已挂载。

---

#### 错误 2：用 `(menu as any).dom` 定位菜单容器

**做法**：通过 `menu.dom` 获取菜单的根 DOM 元素，再查找 `.menu-scroll` 清理分隔线。

**问题**：`menu.dom` 指向的元素并非文档中的 `.menu` 元素。调试日志显示 `menu.dom` 的 `children` 为空数组，而文档中的菜单有 9 个子元素。

**解决**：改为 `document.querySelectorAll('.menu')` 取最后一个（最新的菜单）。

**教训**：Menu 对象的内部属性和文档 DOM 是分离的。不要假设 `menu.dom` 等于文档中渲染的元素。

---

#### 错误 3：只处理了 `file-explorer` 的 `source`

**做法**：`file-menu` 事件只检查 `source === 'file-explorer'`。

**问题**：标签页标题右键也触发 `file-menu` 事件，但 `source` 是 `'tab-header'`，导致标签页菜单不被拦截。

**调试方式**：添加 `console.log` 打印 `source` 参数，发现标签页右键时 `source` 为 `'tab-header'`。

**解决**：增加 `else if (source === 'tab-header')` 分支。

**教训**：`file-menu` 事件的 `source` 参数不仅限于 `'file-explorer'`，还可能是 `'tab-header'`、`'link-context-menu'` 等。需要测试不同场景。

---

#### 错误 4：`onPaneMenu` 只对自身视图生效

**做法**：在 `SidebarHomeView` 中 override `onPaneMenu` 来拦截标签页菜单。

**问题**：`onPaneMenu` 是实例方法，只对当前 View 实例的面板菜单生效。右键 Markdown 编辑器的标签页时，调用的是 MarkdownView 的 `onPaneMenu`，不会触发 SidebarHomeView 的 override。

**解决**：改用 `file-menu` 事件 + `source === 'tab-header'` 来全局拦截。

**教训**：View 的 `onPaneMenu` 不是全局钩子，它只处理该 View 自身的面板菜单。要拦截所有标签页菜单，必须用 workspace 级别的事件。

---

#### 错误 5：分隔线清理时 `isGroupEmpty` 检查直接子元素

**做法**：`isGroupEmpty` 用 `el.children` 检查 group 的直接子元素是否都隐藏。

**问题**：菜单结构是 `.menu-group > .menu-item`，但检查的是 `el.children`，其中可能包含非 `.menu-item` 的元素（如嵌套的 wrapper），导致 `every()` 逻辑错误。

**解决**：改为 `el.querySelectorAll('.menu-item')` 确保只检查菜单项。

**教训**：DOM 结构可能比预期更深。用 `querySelectorAll` 比 `children` 更可靠。

### 关键技术点

#### Obsidian 菜单 DOM 结构

```html
<div class="menu" style="left: Xpx; top: Ypx;">
  <div class="menu-grabber"></div>
  <div class="menu-scroll">
    <div class="menu-group">
      <div class="menu-item tappable" data-section="...">
        <div class="menu-item-icon">...</div>
        <div class="menu-item-title">菜单项标题</div>
      </div>
    </div>
    <div class="menu-separator"></div>
    <div class="menu-group">...</div>
  </div>
</div>
```

#### Menu 对象关键属性

- `menu.items`：MenuItem 数组，每个有 `dom` 属性（孤立 DOM 节点）
- `menu.dom`：Menu 的根元素引用（不一定等于文档中的元素）
- 菜单在 `showAtMouseEvent` 调用后才挂载到文档

#### 事件 source 参数值

| 事件 | source 值 | 说明 |
|------|----------|------|
| `file-menu` | `'file-explorer'` | 文件资源管理器右键 |
| `file-menu` | `'tab-header'` | 标签页标题右键 |
| `file-menu` | `'link-context-menu'` | 链接右键 |
| `editor-menu` | - | 编辑器内容区右键 |

#### 分隔线清理逻辑

需要处理的情况：
1. 首部/尾部的分隔线
2. 相邻的两个分隔线（保留一个）
3. 前后是隐藏项或空 group 的分隔线

检查方式：遍历 `.menu-scroll` 的直接子元素，对每个 `.menu-separator` 检查前后的兄弟元素状态。

#### 错误 6：隐藏菜单项后菜单位置偏移（多次迭代）

**问题**：在屏幕偏下方右键时，Obsidian 将菜单向上翻转（底部对齐鼠标）。隐藏菜单项后高度变小，但 `top` 没变，导致菜单远离鼠标。

##### 尝试 1：强制 reflow

```typescript
menuStyle.style.display = 'none';
menuStyle.offsetHeight;
menuStyle.style.display = '';
```

**失败原因**：`top` 是显式内联样式，reflow 不会重新计算显式设置的 CSS 属性。

##### 尝试 2：MutationObserver + 手动调整 top

**失败原因**：MutationObserver 在菜单 append 到 DOM 时触发，但此时 Obsidian 尚未调用 `showAtPosition` 设置 `top/left`。调整被后续的定位覆盖。

##### 尝试 3：patch menu.showAtPosition

```typescript
const origShow = menu.showAtPosition.bind(menu);
menu.showAtPosition = (position) => {
    origShow(position);
    // 隐藏项 + 调整位置
};
```

**失败原因**：`showAtPosition` 可能不是实际的定位入口，或 `menu.dom` 在调用时还未就绪。

##### 尝试 4：MutationObserver + 50ms setTimeout

```typescript
setTimeout(() => doFilter(menuEl), 50);
```

**结果**：能正确工作，但有 50ms 延迟导致菜单闪烁，且翻转检测逻辑有 bug（`originalTop > originalBottom - height` 永远为 false）。

##### 最终方案：attributes observer + 鼠标位置追踪

**关键洞察**：
1. `childList` observer 触发太早（菜单未定位），需要等 Obsidian 设置 `style` 属性
2. 翻转检测不能靠位置推算，需要直接记录鼠标位置

```typescript
// 1. 持续记录鼠标位置
document.addEventListener('mousemove', (evt) => {
    this.lastMouseY = evt.clientY;
});

// 2. 监听 style 属性变化（Obsidian 设置 top/left 时立即触发，无延迟）
const observer = new MutationObserver(() => {
    const menuEl = document.querySelector('.menu');
    if (!menuEl?.style.top) return;
    observer.disconnect();

    // 3. 通过鼠标到菜单两端的距离判断翻转
    const flipped = Math.abs(lastMouseY - originalBottom) < Math.abs(lastMouseY - originalTop);

    // 4. 隐藏项 + 清理分隔线
    // ...

    // 5. 根据翻转模式重新定位
    if (flipped) {
        newTop = Math.max(0, lastMouseY - newHeight);  // 底部对齐鼠标
    } else {
        newTop = lastMouseY;  // 顶部对齐鼠标
        if (newTop + newHeight > viewportH) {
            newTop = Math.max(0, viewportH - newHeight);
        }
    }
    menuEl.style.top = `${newTop}px`;
});
observer.observe(document.body, { attributes: true, subtree: true, attributeFilter: ['style'] });
```

**教训**：
1. `MutationObserver` 的 `childList` 在 DOM append 时触发，但框架可能在之后才设置定位属性。用 `attributes` + `attributeFilter: ['style']` 可以精确定位到样式设置的时机。
2. 不要用数学关系推算状态（`top > bottom - height` 永远为 false），直接从业务角度获取原始数据（鼠标位置）。
3. 绝对定位元素的 `top` 是显式样式，reflow 不会重新计算，必须手动设置。
